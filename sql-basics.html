1 What is SQL, really?

Every app you use — Instagram, Swiggy, your college portal — stores information somewhere. That "somewhere" is a database. SQL is how you talk to it.

SQL = Structured Query Language (say "S-Q-L" or "sequel"). A query is just a sentence you send to the database. It's declarative: you say what you want, not how to find it.

It works on a relational database — data kept in tables that can be linked together. Think of an Excel workbook with superpowers.

💡 Why learn it?SQL has been around since the 1970s and is still one of the most requested skills in interviews, backend, data and analytics jobs. Learn it once, use it everywhere.

3 SELECT — asking questions

The command you'll write 90% of the time. Pattern: SELECT what you want FROM which table.

-- every column, every row  (* means "everything")
SELECT * FROM students;

-- only some columns
SELECT name, city FROM students LIMIT 3;
Result of the second query

Handy tricks

-- DISTINCT removes duplicates
SELECT DISTINCT city FROM students;
-- AS gives a column a nickname (an alias); you can also do maths
SELECT name AS student, marks + 5 AS grace_marks FROM students LIMIT 2;
📖 Jargon checkA clause is a building block (SELECT, FROM…). An alias is a temporary nickname. SQL keywords are not case-sensitive, but writing them in CAPS makes queries easier to read. End statements with ;

4 WHERE — filtering rows

Without WHERE you get every row. With it, you get only the rows that pass your test — like a bouncer at a club. 🕴️

SELECT name, marks FROM students WHERE marks >= 85;
Comparison operators
OperatorMeaning

AND / OR / NOTcombine conditions

SELECT name, city FROM students WHERE city IN ('Mysuru', 'Chennai');
SELECT name, marks FROM students WHERE marks BETWEEN 70 AND 85;
-- names that END with the letter a
SELECT name FROM students WHERE name LIKE '%a';
🚨 The NULL trap (everyone falls for it once) WHERE dept_id = NULL returns nothing, ever. NULL means "unknown", and nothing is equal to unknown — not even another NULL. Use IS NULL. Likewise, dept_id <> 1 will skip Dev, because comparing unknown to 1 gives "unknown", not "true".
SELECT name FROM students WHERE dept_id IS NULL;

5 ORDER BY & LIMIT — sorting and trimming

Databases don't promise any order unless you ask for one. ORDER BY sorts; LIMIT keeps only the first N rows — perfect for "Top 3" lists. 🏆

SELECT name, marks FROM students ORDER BY marks DESC LIMIT 3;
  • ASC = smallest first (default), DESC = largest first.
  • Sort by several columns: ORDER BY city ASC, marks DESC — sort by city, and break ties using marks.
  • Some databases (SQL Server) use TOP 3 and Oracle uses FETCH FIRST 3 ROWS ONLY instead of LIMIT — same idea, different dialect. A dialect is just a flavour of SQL.

6 Aggregate functions — crunching many rows into one

An aggregate function squashes a pile of rows into a single answer.

COUNT(*) how many rows
COUNT(col) how many non-NULL values
SUM(col) total
AVG(col) average
MIN(col) smallest
MAX(col) largest
SELECT COUNT(*) AS total, ROUND(AVG(marks), 1) AS avg_marks, MAX(marks) AS top
FROM students;
💡 COUNT(*) vs COUNT(dept_id)On our table COUNT(*) is 8 but COUNT(dept_id) is 7 — aggregates quietly ignore NULLs (except COUNT(*)).

7 GROUP BY & HAVING — stats per category

"How many students per city?" "Average marks per department?" — that's GROUP BY. It sorts rows into buckets, then runs the aggregate on each bucket. 🪣

SELECT city, COUNT(*) AS students
FROM students
GROUP BY city;
🧠 The golden ruleEvery column in your SELECT must either appear in GROUP BY or be wrapped in an aggregate function. Otherwise the database can't decide which value to show for the bucket.

WHERE vs HAVING

WHERE filters rows before grouping.
"Ignore students under 60."
HAVING filters groups after aggregating.
"Keep only departments whose average > 80."
SELECT dept_id, ROUND(AVG(marks), 2) AS avg_marks
FROM students
GROUP BY dept_id
HAVING AVG(marks) > 80;

8 INSERT, UPDATE, DELETE — changing data

So far we only looked. Now we change things. With great power comes great responsibility. 🕷️

-- add a new row
INSERT INTO students (id, name, dept_id, marks, city, age)
VALUES (9, 'Tara', 2, 85, 'Mysuru', 19);

-- change existing rows
UPDATE students SET marks = 90 WHERE name = 'Ravi';

-- remove rows
DELETE FROM students WHERE id = 6;
☠️ Always, always, ALWAYS use WHERE with UPDATE and DELETE UPDATE students SET marks = 0; sets everyone's marks to zero. DELETE FROM students; wipes the whole table. Pro habit: first write a SELECT with the same WHERE and check which rows come back, then change it to UPDATE/DELETE.
🔄 Jargon: transactionA transaction lets you wrap changes in BEGIN … COMMIT (save) or ROLLBACK (undo). It's your safety net.

Before storing data, you design the blueprint — the schema.

CREATE TABLE courses (

  title      VARCHAR(80)  NOT NULL,
  credits    INT          DEFAULT 3 CHECK (credits > 0),
  fee        DECIMAL(8,2),
  start_date DATE

Constraints rule the table: NOT NULL (value required), UNIQUE (no duplicates), DEFAULT (fallback value), CHECK (custom rule). A constraint is a bouncer built into the table itself.

DELETE vs TRUNCATE vs DROP

DELETE removes some or all rows, can use WHERE, can be rolled back (usually).
TRUNCATE quickly empties all rows, keeps the table.
DROP TABLE destroys the table itself — rows and structure.
ALTER TABLE modifies structure, e.g. ADD COLUMN email VARCHAR(80).

10 Keys — how tables recognise each other

Imagine two students named "Asha". How does the database tell them apart? With a key. 🔑

🥇 Primary Key (PK)

A column whose value uniquely identifies each row. Never duplicate, never NULL. One per table. Example: students.id.

🔗 Foreign Key (FK)

A column that points to the primary key of another table. It creates the link. Example: students.dept_id → departments.dept_id.

🛡️ Referential integrityA foreign key stops you from adding a student with dept_id = 99 if no department 99 exists, and blocks deleting a department that students still belong to. The database protects itself.

Why split data into two tables? Storing "Computer Science & Engineering" in every student row wastes space and invites typos. Store it once, point to it by ID. This idea is called normalization.

11 JOINs — stitching tables together

Because data lives in separate tables, we need a way to put it back together in a query. A JOIN does exactly that, matching rows using the ON condition.

SELECT s.name, d.dept_name
FROM students s
INNER JOIN departments d ON s.dept_id = d.dept_id;

👆 s and d are table aliases — short nicknames so you type less.

INNER JOIN — only rows that match on both sides.
LEFT JOIN — all left rows; unmatched right side becomes NULL.
RIGHT JOIN — all right rows; unmatched left side becomes NULL.
FULL OUTER JOIN — everything from both sides.
🧩 Real-life use"Show departments that have no students": LEFT JOIN from departments to students, then add WHERE s.id IS NULL. Try the LEFT/RIGHT toggle above to see why it works!

12 Staying safe: SQL injection 🛡️

The #1 beginner mistake in real apps: gluing user input directly into a query string.

⚠️ DEVELOPMENT ONLY - NOT SECURE FOR PRODUCTIONThe example below is intentionally vulnerable so you can recognise it. Never ship code like this.
# ❌ VULNERABLE — string concatenation
name = input("Enter name: ")
query = "SELECT * FROM students WHERE name = '" + name + "'"
cursor.execute(query)

# An attacker types:   x' OR '1'='1
# The database runs:   SELECT * FROM students WHERE name = 'x' OR '1'='1'
# → '1'='1' is always true, so EVERY row leaks.

SQL injection happens when input is mixed with SQL code. The fix is to keep code and data separate using a parameterized query:

# ✅ SAFE — placeholders (?) keep input as pure data
name = input("Enter name: ").strip()
cursor.execute("SELECT * FROM students WHERE name = ?", (name,))
Safety checklist
  • ✅ Always use parameterized queries / an ORM — never string concatenation.
  • ✅ Validate input (type, length, allowed characters) before it reaches the database.
  • ✅ Least privilege: the app's database user should only get the permissions it needs (e.g. SELECT on specific tables), not admin rights.
  • ✅ Keep passwords and connection strings in environment variables or a secrets manager, never in code or Git.

13 Cheat sheet & the order SQL really runs

You write SQL in one order, but the database thinks in another. Knowing this explains many "why doesn't this work?" errors.

✍️ How you write it
SELECT→FROM→WHERE→GROUP BY→HAVING→ORDER BY→LIMIT
🧠 How it runs
FROM / JOIN→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT
Why it mattersWHERE runs before SELECT, so you can't use a SELECT alias inside WHERE. And WHERE runs before grouping, so it can't contain COUNT() or AVG() — that's HAVING's job.

Read

SELECT col1, col2
FROM table
WHERE condition
ORDER BY col DESC
LIMIT 10;

Summarise

SELECT col, COUNT(*)
FROM table
GROUP BY col
HAVING COUNT(*) > 1;

Change

INSERT INTO t (a,b) VALUES (1,'x');
UPDATE t SET a = 2 WHERE id = 1;
DELETE FROM t WHERE id = 1;

Join

SELECT a.x, b.y
FROM a
LEFT JOIN b ON a.id = b.a_id;
